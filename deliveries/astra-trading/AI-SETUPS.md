# Astra Trading — وحدة "الصفقات المقترحة من الـ AI" (AI-Proposed Setups)

> الحالة: **مرحلة تخطيط** · ملحق لوثيقة `PLAN.md` · تاريخ: 2026-11-13

---

## 1. الفكرة كما طلبها المالك

> وحدة داخل التطبيق اسمها **"الصفقات المقترحة من الـ AI"**:
> الـ AI يراقب سوق الذهب بنفسه، **ينتظر الفرصة المناسبة** (القاع/القمة جاهزة)،
> وعندما تتوفر الفرصة يبعت **مقترح صفقة**: «إذا وصل السعر إلى X بيع/اشتري،
> الستوب هنا، الأهداف هنا».
> **المستخدم لا يحادث الـ AI مباشرة** — الـ AI يبعت من تلقاء نفسه.
> يُترك **API** مربوط بالمشروع، يُعطى لـ **وكيل AI** (بأدواته) يحلّل ويبعت للتطبيق.

**تقييمي:** الفكرة قوية جداً وتخلق قيمة لحظية حقيقية. لكن "الصفقات" بلغة الجزم = أعلى مخاطرة قانونية وسمعية. الحل: نفس الفكرة بصياغة **سيناريوهات مقترحة معلنة القواعد + سجل أداء شفّاف قابل للتدقيق**. هيك توصل الفكرة كاملة وتبقى محميين.

## 2. المبدأ الحاكم (الحجر الأساس)

| المبدأ | التفصيل |
|---|---|
| **الشفافية الكاملة** | كل مقترح يُسجَّل بوقته ولا يُعدَّل بعد النشر — سجل غير قابل للتلاعب |
| **السجل الحقيقي** | كل مقترح يُقيَّم آلياً على بيانات السعر الفعلية → WIN/LOSS/BE — **بدون تجميل** |
| **لا تنفيذ آلي** | التطبيق **لا** يتداول ولا يوصل لحساب المستخدم — المستخدم يقرر بنفسه |
| **الإفصاح** | «تحليل تقني تعليمي — ليس نصيحة استثمارية» على كل مقترح |
| **الانضباط** | سقف لعدد المقترحات النشطة → الـ AI يختار الأفضل، لا يغرق المستخدم |

**هذا هو الفرق بيننا وبين 90% من "قنوات الإشارات": نحن ننشر أداءنا الحقيقي ونتحمّله.**

## 3. دورة حياة المقترح (Setup Lifecycle)

```
        ┌──────────┐
        │  DRAFT   │  الوكيل يجهّز (مسودة داخلية، اختياري)
        └────┬─────┘
             │ POST /setups
        ┌────▼─────┐   السعر لسا ما وصل
        │ PROPOSED │───────────────► EXPIRED (انتهت صلاحيته)
        └────┬─────┘                     ▲
             │ السعر لمس منطقة الدخول      │
        ┌────▼─────┐                       │
        │ TRIGGERED│  (أصبح فعّالاً)        │
        └────┬─────┘                       │
             ├──────────────► STOPPED  (ضرب الستوب → LOSS)
             ├──────────────► TP1/TP2/TP3 (أهداف → WIN جزئي/كامل)
             ├──────────────► BREAKEVEN
             └──────────────► INVALIDATED (شرط الإبطال تحقق قبل الدخول)
```

**كل انتقال حالة يُسجَّل بوقت + سعر + سبب.** لا تعديل يدوي على مقترح منشور أبداً.

## 4. الحقول الإلزامية لكل مقترح (Data Model)

| الحقل | الوصف | إلزامي |
|---|---|---|

| `direction` | long / short | ✅ |
| `entry_type` | market / limit / stop | ✅ |

| `stop_loss` | الستوب | ✅ |
| `take_profits` | أهداف متعددة [TP1, TP2, TP3] | ✅ |
| `validity_until` | صلاحية المقترح (وقت) | ✅ |
| `invalidation` | شرط إبطال المقترح | ✅ |
| `risk_reward` | R:R محسوب | ✅ |
| `timeframe` | 5m / 15m / 1h / 4h / 1D | ✅ |

## 5. عقد الـ API (Ingestion Contract)

الـ API **write-only** لوكيل التحليل — ما بيقرأ بيانات مستخدمين.

```
POST /api/v1/setups
Headers:
  X-Agent-Key: <مفتاح الوكيل>          # مصادقة
  X-Idempotency-Key: <uuid>            # منع التكرار
  X-Signature: <hmac>                  # (اختياري) توقيع الطلب
Body: { ...الحقول في القسم 4... }
```

**الاستجابات:**
| الرمز | المعنى |
|---|---|
| `201` | أُنشئ المقترح (يرجع id + حالته) |
| `200` | إعادة إرسال مطابقة (idempotent) — لا تكرار |
| `400` | بيانات ناقصة/غير صالحة (وقف أعلى من دخول، إلخ) |
| `401` | مفتاح وكيل غير صالح |
| `409` | تعارض (مقترح نشط على نفس الأصل بنفس الاتجاه) |
| `429` | تجاوز الحد (سقف المقترحات النشطة / معدّل الطلبات) |

**نقاط إضافية (قراءة عامة فقط):**
- `GET /api/v1/setups?status=active` — المقترحات النشطة
- `GET /api/v1/track-record` — السجل العام (مفتوح للجميع → بناء الثقة)
- `POST /api/v1/setups/{id}/cancel` — إلغاء (يُسجَّل ولا يُحذف)

**التحقق الآلي (Validation) يرفض:** وقف فوق الدخول للشراء · أهداف بغير اتجاه · R:R أقل من حد أدنى (مثلاً 1.0) · صحة زمنية غلط · إحداثيات خارج نطاق معقول للسعر.

## 6. أدوات وكيل التحليل (AI Agent Toolbox)

الوكيل يُزوَّد بأدوات حقيقية (لا تخرّج عشوائي):

| الأداة | الوظيفة |
|---|---|
| `fetch_candles(symbol, tf, n)` | جلب الشموع من المصدر الموثوق |
| `find_levels(tf)` | دعم/مقاومة (تجميع قمم/قيعان) |
| `find_liquidity(tf)` | قمم/قيعان متساوية · جلسات · أرقام مستديرة |
| `volatility(tf)` | ATR + مقارنة بسياق |
| `session_context()` | أي جلسة الآن + مدى الجلسات |
| `build_setup(...)` | يبني مقترحاً صحيحاً بنيوياً (يرفض غير المنطقي) |
| `submit_setup(...)` | يبعته للـ API |
| `wait_for_opportunity()` | **ينتظر** ولا يبعث شيئاً إن لم تتوفر فرصة |

**قاعدة ذهبية:** الوكيل **يبعث "لا شيء"** إذا ما في فرصة. عدم الإرسال قرار صحيح ومطلوب.

## 7. أفكار إضافية (هي جوهر سؤالك) — اقتراحاتي

### 7.1 🧪 الوضع الظلّي (Shadow Mode) — أهم فكرة
قبل النشر للمستخدمين، الوكيل يشتغل **فترة تجريبية** ويسجّل مقترحاته **بدون إظهارها للمستخدمين**، وتُقيَّم آلياً.
**الفائدة:** نبني سجل أداء حقيقي قبل ما ناخد ولا دولار — نعرف هل الوكيل فعّال فعلاً. إذا ضعيف، نعدّله قبل ما ينزل. **هذا يحمينا من الفشل العلني.**

### 7.2 📊 سجل الأداء العام (Public Track Record)
صفحة يراها أي زائر: عدد المقترحات · نسبة الربح · متوسط R:R · أقصى سلسلة خسائر · منحنى الأداء.
**الفائدة:** هذا هو **أقوى سلاح ضد "نصب"** — المستخدم يشوف النتائج الحقيقية بنفسه. وهو رد مباشر على «منشان العالم تعرف إنه مو نصبي».

### 7.3 🧾 مراجعة ما بعد النتيجة (Post-Mortem)
بعد كل مقترح، ملاحظة قصيرة بالعربي: «نجح لأن…» / «فشل لأن…».
**الفائدة:** تعليمي + يبني ثقة + يُحسّن الوكيل.

### 7.4 🚦 قاطع الدائرة (Circuit Breaker)
إذا تدهور أداء الوكيل المتدحرج (مثلاً 3 خسائر متتالية أو ربحية سلبية خلال أسبوع) → **إيقاف النشر تلقائياً** وإشعار المالك.
**الفائدة:** يحمي السمعة والمال. لازم يكون إلزامي.

### 7.5 ⏳ عرض "الـ AI يراقب الآن"
بدل شاشة فاضية، يعرض: «الـ AI يراقب السوق… لا توجد فرصة مطابقة حالياً».
**الفائدة:** يبيّن إنه **منضبط لا عشوائي** — وهذا بحد ذاته قيمة.

### 7.6 🎚️ سقف المقترحات النشطة
حد أقصى (مثلاً 3) مقترحات نشطة. يجبر الـ AI يختار **الأفضل**، ويمنع إغراق المستخدم.
**الفائدة:** جودة > كمية.

### 7.7 🔔 التنبيهات
إشعار (بريد/تليجرام/داخل التطبيق) عند: مقترح جديد · تفعيل · ضرب هدف/ستوب.
**الفائدة:** القيمة الأساسية للمستخدم — يعرف بالوقت المناسب.

### 7.8 📈 وضع الورق (Paper Trading) للمستخدم
المستخدم يجرّب **يتبّع** المقترحات على ورق ويشوف نتيجته الافتراضية.
**الفائدة:** يبني الثقة قبل ما يدفع، ويحمّلنا مسؤولية صفر (لا أموال حقيقية).

### 7.9 🏅 الترتيب حسب المصدر (Multi-Agent Ranking)
بما إنه API مفتوح لعدة وكلاء → التطبيق يرتّب المصادر حسب أدائها الحقيقي.
**الفائدة:** نظام تطور طبيعي — الأفضل يبرز. (فكرة v2/v3)

### 7.10 🔒 وضع "يتطلب اعتماد" (Approval Mode)
مفتاح تشغيل: `auto-publish` أو `require-approval` (CEO/المالك يعتمد قبل النشر).
**الفائدة:** في البداية نشتغل بمراجعة، وبعد ما يثبت الأداء ننتقل تلقائي.

### 7.11 💰 التسعير مرتبط بالوحدة
- **مجاني:** الشارت + الدعوم/المقاومات + المقترحات **متأخرة** أو مبهمة.
- **Pro ($19):** المقترحات **لحظية كاملة** + التنبيهات + حاسبة المخاطرة.
**الفائدة:** أفضل ميزة تصير سبب الاشتراك (value gate واضح).

### 7.12 🧮 حاسبة المخاطرة مدمجة بالمقترح
كل مقترح يجي معه: «بمخاطرة 1% من حسابك = حجم كذا».
**الفائدة:** يحوّل المقترح لقرار قابل للتنفيذ بأمان.

### 7.13 🧭 فلترة السياق (Session Filter)
المقترحات تُعلَّم: «مناسب لجلسة لندن فقط».
**الفائدة:** دقة أعلى — الذهب حساس جداً للجلسات.

## 8. الأمن (Security) — حرج لهذه الوحدة

| البند | التنفيذ |
|---|---|
| مصادقة الوكيل | مفاتيح API **مُجزَّأة (hashed)** في القاعدة، غير قابلة للاسترجاع |
| النطاق (Scope) | مفتاح الوكيل **يكتب مقترحات فقط** — لا يقرأ مستخدمين ولا بيانات دفع |
| الإلغاء (Revoke) | إمكانية إلغاء أي مفتاح فوراً |
| منع التكرار | `idempotency_key` إلزامي |
| معدّل الطلبات | Rate limit لكل مفتاح |
| سجل تدقيق | كل استدعاء يُسجَّل (وقت، مفتاح، نتيجة) |
| فصل الصلاحيات | الوكيل ما بيلمس: الدفع، بيانات المستخدمين، الصلاحيات |
| الأسرار | المفاتيح في Secret Store، **لا** في الكود ولا المستودع |

## 9. المخاطر الخاصة بهذه الوحدة

| المخاطرة | المعالجة |
|---|---|
| أداء ضعيف → ضرر سمعة | وضع ظلّي أولاً + سجل شفّاف + قاطع دائرة |
| تصنيف "نصيحة مالية" | إفصاح + لا تنفيذ + صياغة "سيناريو" + شروط استخدام |
| إغراق المستخدم | سقف مقترحات نشطة + معدّل |
| انقطاع الوكيل | عرض «آخر تحديث» بصدق + حالة "غير متصل" |
| تحيّز/تلاعب بالسجل | سجل غير قابل للتعديل + تقييم آلي من بيانات السوق |
| خطأ في البيانات | تحقق صحة المصدر + رفض المقترحات الشاذة |

## 10. الأسئلة المفتوحة (للنقاش مع المالك)

1. **من يملك وكيل التحليل؟** نبني نحن وكيل Astra الداخلي (قسم تحليل)؟ أم تزوّدنا بوكيل خارجي؟ (اقتراحي: **نحن نبنيه** كقسم داخلي، والـ API يبقى مفتوحاً لأي وكيل).
2. **وضع الإطلاق:** نبدأ **ظلّي** (تسجيل بلا نشر)؟ أو نشر فوري؟
3. **الاعتماد:** `auto-publish` أم `require-approval` في البداية؟
4. **سقف المقترحات النشطة:** 3؟ 5؟
5. **التقييم:** نعتمد TP1 للنتيجة أم المتوسط المرجّح للأهداف؟
6. **المجاني/المدفوع:** المقترحات **متأخرة للمجاني** أم **مقفلة تماماً** على Pro؟

## 11. الخطوة التالية

بعد استلام **مصدر الشموع** + تأكيد القرارات أعلاه:
1. تصميم مخطط قاعدة البيانات (setups + lifecycle + outcomes).
2. بناء الـ API (`POST /api/v1/setups` + تحقق + idempotency + سجل).
3. بناء أدوات الوكيل (`find_levels` / `find_liquidity` / `build_setup` / `submit_setup`).
4. تشغيل **الوضع الظلّي** وبناء سجل الأداء الحقيقي.
5. بعد إثبات الأداء → النشر + الربط بالاشتراكات.
